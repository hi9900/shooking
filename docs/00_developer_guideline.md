### 프로젝트 목표

사용자에게 상품 상세 페이지, 장바구니, 카드 등록 및 결제 흐름에 이르는 전반적인 쇼핑 경험을 끊김 없이(Seamless) 제공하는 것을 목표로 합니다.

# 시스템 아키텍처
<!-- 
> 시스템의 전체적인 구조와 각 컴포넌트가 어떻게 연동되는지를 도식화하여 설명합니다. 이전 문서에서 작성했던 내용이 있다면 링크를 정리해하셔도 좋습니다.

이 프로젝트는 **CSR(Client-Side Rendering)** 방식의 Single Page Application(SPA) 아키텍처를 따릅니다.

# 개발 환경 설정 및 규칙

> 개발을 시작하기 위해 필요한 환경 설정에 대한 자세한 단계를 포함합니다. 프로젝트 주차가 진행되면서 조금씩 추가되거나 변경된 요소를 한 번에 정리합니다. 또한 코드 저장소의 구조, 사용되는 브랜치 전략, 커밋 메시지 규칙 등을 설명합니다.

### 1. 개발 환경 설정

| 항목 | 명령어/설명 | 유의사항 |
| :--- | :--- | :--- |
| **의존성 설치** | `npm install` | 프로젝트 시작 전 필수 |
| **개발 서버 실행** | `npm run dev` | 로컬에서 개발 서버 실행 |
| **테스트 실행** | `npm test` | 모든 유닛 테스트 및 스냅샷 테스트 실행 |
| **TS 설정** | **`@types/node` 설치 확인** | Node.js 내장 모듈 사용 시 필수 (`util` 모듈 등) |
| **Jest 설정** | `setupTests.ts` 파일에 **`TextEncoder` 폴리필**이 적용되어 있어야 합니다. | Node 환경에서 브라우저 API 호출 시 테스트 에러 방지 |

### 2. 코드 저장소 및 브랜치 전략

* **브랜치 전략:** **GitHub Flow**를 기본으로 사용합니다.
    * `main`: 프로덕션 배포가 가능한 안정적인 코드만 유지합니다.
    * `feature/*`: 모든 기능 개발은 `main`에서 시작한 피처 브랜치에서 진행됩니다.
    * `fix/*`: 버그 수정은 별도의 `fix` 브랜치에서 진행합니다.

### 3. 커밋 메시지 규칙

간결하고 설명적인 커밋 메시지를 위해 다음의 타입을 사용합니다. (Conventional Commits 경량화 버전)

| Type | 설명 | 예시 |
| :--- | :--- | :--- |
| **FEAT** | 새로운 기능 추가 | `FEAT: 카드 등록 폼 유효성 검사 로직 추가` |
| **FIX** | 버그 수정 | `FIX: CartItem 수량 1개일 때 마이너스 버튼 비활성화 수정` |
| **REFACTOR** | 기능 변경 없는 코드 구조 개선 | `REFACTOR: CartPage 로직 useFormInput 훅으로 분리` |
| **STYLE** | CSS, UI 단순 변경 | `STYLE: OrderSummary 총액 텍스트 크기 조정` |
| **CHORE** | 빌드 설정, 라이브러리 업데이트 등 | `CHORE: jest 설정에 TextEncoder polyfill 추가` |

# 프로젝트에서 중요했던 지점
<!-- 
> 프로젝트 개발에 있어서 가장 중요했던 결정이나 방향성을 설명합니다.
-->

1.  **의존성 역전(Dependency Inversion) 원칙 적용:**
    * 재사용성이 높은 `ProductCard` 같은 컴포넌트가 `useNavigate`와 같은 라우팅 로직을 **직접 사용하지 않도록** 설계했습니다.
    * 대신, `onClickButton`과 같은 prop을 통해 상위 컴포넌트(페이지)가 네비게이션 로직을 전달하도록 하여, 컴포넌트의 **테스트 용이성**을 극대화했습니다.
2.  **Derived State의 효율적인 관리:**
    * `CartContext` 내부에서 `subtotal`, `shipping`, `total`과 같은 계산된 값들을 `useMemo`로 래핑하여, `cart` 배열이 변경될 때만 계산이 일어나도록 최적화했습니다. 이는 불필요한 연산을 방지합니다.
3.  **UI/Logic 표준화:**
    * `useFormInput` 커스텀 훅을 만들어 모든 폼 입력 상태 관리를 표준화하고, 복잡한 포맷팅/유효성 검사 로직을 중앙 집중화하여 컴포넌트를 깔끔하게 유지했습니다.

# 다른 문서를 어떻게 참고하면 좋을지에 대한 가이드
<!-- 
> 기존 문서를 참고하는 법과 문서 갱신에 대한 절차를 안내합니다.
-->

1.  **데이터 모델 확인:**
    * `src/types/` **TypeScript 인터페이스**를 참조하여 데이터의 정확한 형태와 속성을 확인해야 합니다.
2.  **비즈니스 로직 확인:**
    * 복잡한 로직(배송비 계산, 수량 증감)은 `src/contexts/CartContext.tsx` 파일에 집중되어 있으니, 이 파일을 중심으로 확인하십시오.
3.  **문서 갱신 절차:**
    * 이 개발 가이드라인(`Developer Guidelines`) 또는 `README.md`에 영향을 주는 **아키텍처 변경, 주요 기술 스택 추가/변경, 핵심 로직 변경**이 발생할 경우, **반드시 PR에 해당 내용을 요약하여 문서 수정을 포함**해야 합니다.
